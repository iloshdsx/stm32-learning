## 1. "编译失败"其实失败在最后一行 —— 打印大小

**现象**（`烧录.bat` 的输出，注意**中间一个字都没有**）：

```
  AS  startup_stm32f103c8tx.s
  LD  test_led.elf

make: *** [Makefile:55: test_led.elf] Error 1
********** 编译失败 **********
```

看着像链接失败，但**没有任何报错文字**，这就说明"看上去像"的那个判断是错的。

**排查过程（思路比结论值钱）**

1. **先看产物在不在**：
   `D:\STM32\test_led_build\test_led.elf` —— **在，而且大小正常**。
   → 链接根本没失败。这一步就把 90% 的错误方向排除了。
2. **再看行号**：`Makefile:55`，去数第 55 行是什么：

   ```
   51: $(TARGET): $(OBJS)
   52: > @echo   LD  $@
   53: > @$(CC) -o $@ $(OBJS) $(LDFLAGS)      ← 链接（成功）
   54: > @echo.
   55: > @$(SZ) $@                            ← 打印大小（失败的是这行！）
   ```

3. 结论：**失败的是"打印大小表"这个锦上添花的步骤**。

**根因**：`arm-none-eabi-size` 去读刚刚才写完的 elf 文件，
被杀软 / 索引器瞬时锁住 → 偶发 `Permission denied`。
它只是打印一张表，却把整个脚本判成了"编译失败"。

**修法**：在 make 里给这行前面加一个 `-`（含义：**这步失败也别管**）

```
> -@$(SZ) $@
```

**教训（记住这两条）**

- **`make: *** [Makefile:NN: 目标] Error N` 里的 `NN` 就是"失败的那一行"**
  —— 别猜，去数行号。数完常常发现"根本不是你以为的那一步"。
- **报错是空的时候，先看产物生成了没有**：能立刻区分"真失败"和"假失败"。

## 2. ST-Link 连不上（2026-10-07 · 已解决，根因在文末）

### 现象演变（关键在这张表）

| 阶段 | 报错 | 含义 |
|---|---|---|
| 一开始 | `Error: Unable to get core ID` | ST-Link **认到了**，但连不上芯片 |
| 换线 / 调换 SWCLK-SWDIO 之后 | `Error: No debug probe detected` | **连 ST-Link 本身都找不到了** |

**报错变了 = 问题的层次变了。** 别再照着旧思路查 ——
这两个错一个在"下载器 ↔ 芯片"这一层，一个在"电脑 ↔ 下载器"这一层。

### 已经排除掉的

- **板子没坏**：板载 LED 一秒一闪 → 芯片在正常运行我们烧进去的程序
- **驱动没坏**：能读出 ST-Link 的 SN（`37FF71064E5734369C0C1A43`）和固件版本（`V2J37S7`）→ USB 通信正常
- **没被别的程序占用**：CubeIDE 虽然开着，但没有 GDB server、没有监听端口（查过 61234 等端口）

### 当时的判断

从"能认到但连不上"变成"完全找不到"，很像 **USB 连接 / 供电不稳**
—— 克隆版 ST-Link 非常吃 USB 口（前面板、扩展坞、延长线都会出问题）。

### 还没做的验证（明天接着来）

- [ ] 换机箱**后置** USB 口（不走前面板 / 扩展坞 / 延长线）
- [ ] 插到**另一台电脑**，看能不能被识别 → 能就是本机 USB 的事，不能就是 ST-Link 挂了
- [ ] **万用表**量那 4 根线的通断（到货了就做，5 秒出结论）
- [ ] 换**第二块 Blue Pill** 交叉验证（手里有两块）
- [ ] 最后手段：重启电脑复位 USB 控制器

### 顺便排除掉的坑

- `Unable to get core ID` 最常见的成因是 **SWCLK / SWDIO 插反** ——
  这两根对调**烧不了东西**，是最低成本的一次尝试，值得先做。
- **GND 最容易松、又最容易忽略**：漏了 GND，ST-Link 就是认不到板子。
- **千万别把 5V 接到板子上** —— 板子是 3.3V 的。

### 根因 & 解决（2026-10-07 凌晨 · 当场破案）

**根因：那 4 根线里 `3V3` 和 `GND` 接反了。**

等于把板子的电源正负颠倒 —— ST-Link 的 3.3V 被直接短路，电流拉爆，
ST-Link 内部电压塌掉 → 灯灭、下载器从电脑上消失。

#### 最硬的一条判据（记住这条就够）

> **ST-Link 单独插 USB 灯亮，一接上板子就灯灭 / 发烫 → 一定是短路。**
> 不用怀疑电脑、不用怀疑驱动。

**发烫 = 电流大 = 短路。** "灯灭"和"发烫"是同一件事的两种表现。

#### 现象演变全表

| 阶段 | 现象 / 报错 | 含义 |
|---|---|---|
| 一开始 | `Error: Unable to get core ID` | ST-Link **认到了**，但连不上芯片 |
| 调换 SWCLK-SWDIO 后 | `Error: No debug probe detected` | **连 ST-Link 本身都找不到了** |
| 逐渐加剧 | ST-Link 灯灭 + **发烫** | **供电被短路拉垮** |
| 修好接线 | `Device ID 0x410` ✅ | 一次通过 |

#### 逐根接法（不用万用表就能定位短路）

**先拔掉 USB 再动手**；通电时间控制在 1~2 秒，每接一根看一次 ST-Link 的灯：

1. 只接 `GND` → 灯应还亮
2. 再接 `3V3` → 灯应还亮，且板子红色 `PWR` 灯亮
   - **灯灭 / 发烫** → 这两根反了，或板子有连锡短路
3. 再接 `SWCLK` → 看灯
4. 再接 `SWDIO` → 看灯

**判据**

- `GND` + `3V3` 就出问题 → 短路在**板子**上（查排针有没有连锡）
- 加上 `SWCLK` / `SWDIO` 才出问题 → 短路在**线序**

#### 顺手学到的两条命令

```powershell
# 看电脑有没有认出 ST-Link（不用打开 CubeIDE）
STM32_Programmer_CLI.exe --list

# 只连芯片、不烧东西，验证 SWD 通不通
STM32_Programmer_CLI.exe -c port=SWD mode=normal
```

#### 今晚多排除掉的一条

- **程序没锁调试口**：`main.c` 只用了 `PC13`（灯）和 `PA0`（按键），
  **完全没碰 `PA13` / `PA14`**（SWD 的那两根）→ "程序把调试口占了"这条不成立。

#### 血的教训

- **别"整排对调"**：那不是换 `SWCLK`/`SWDIO`，是把 `3V3` 和 `GND` 一起反接，
  会烧板子 / 烧 ST-Link。
- **两块板子的丝印顺序不一定一样**，必须**按丝印一根一根接**，
  不能按"第 1 对第 1"整排对。
- 短路的代价是**发烫**，而发烫是会**真的烧掉**硬件的。
  发现发烫，第一件事永远是**拔**。
